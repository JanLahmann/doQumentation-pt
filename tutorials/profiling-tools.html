Ferramentas para traçar o perfil, personalizar e inspecionar experimentos

Estimativa de uso: 10 minutos em um processador Heron r2 (OBSERVAÇÃO: esta é apenas uma estimativa. Seu tempo de execução pode variar.)

Para obter bons resultados de um computador quântico, você precisa de mais do que um circuito bem projetado. O estado atual do dispositivo, como seu circuito é agendado, o ruído que o circuito sofre e quando e como seu job é executado na unidade de processamento quântico (QPU) afetam a qualidade dos resultados. O Qiskit e o IBM Quantum® Compute Service oferecem um conjunto crescente de ferramentas para desenvolvedores que expõem essas informações. Você pode usar essas ferramentas para agir com base nelas antes de gastar tempo de QPU em um experimento completo e para depurar um experimento concluído.

Este tutorial usa um único experimento de ponta a ponta para mostrar como combinar essas ferramentas em cada etapa de um fluxo de desenvolvimento típico. Nem toda ferramenta é útil para todo experimento, então escolha as ferramentas que respondem às dúvidas que você tem sobre a sua própria carga de trabalho.

O fluxo de trabalho é o seguinte:

  1. Preparar um circuito espelho de uma evolução temporal trotterizada de um modelo de Ising linear com campo transversal.

  2. Selecionar um backend com um conjunto alternativo de dados de calibração projetado para métodos de mitigação de erros baseados em um modelo de ruído.

  3. Executar experimentos de benchmarking do dispositivo para que o transpilador use propriedades atualizadas do dispositivo ao selecionar um layout.

  4. Inspecionar as informações de temporização do circuito agendado.

  5. Aprender modelos de ruído de Pauli-Lindblad e de leitura para o circuito.

  6. Executar simulações locais sem ruído, sem mitigação e com mitigação. As simulações com ruído usam o modelo de ruído aprendido para mostrar quanta melhoria você pode obter com os métodos de mitigação de erros selecionados. Este tutorial usa cancelamento probabilístico de erros (PEC) e Twirled Readout Error eXtinction (TREX).

  7. Obter uma estimativa de uso sem executar em uma QPU, para verificar se você precisa ajustar o experimento para caber no seu orçamento.

  8. Iniciar uma sessão e disparar a calibração para que o experimento use os dados de calibração mais recentes.

  9. Executar o experimento na QPU usando o Estimator e comparar os resultados do hardware com a prévia simulada.

  10. Inspecionar os spans de execução para ver se há lacunas significativas entre grupos de execuções (chunks).

Requisitos​

Antes de iniciar este tutorial, verifique se você tem o seguinte instalado:

  • Qiskit SDK v2.3 ou posterior, com suporte a visualização

  • qiskit-ibm-runtime v0.52.1 or later (pip install qiskit-ibm-runtime)

  • Qiskit Aer (pip install qiskit-aer)

  • Plotly (pip install plotly)

  • Qiskit Device Benchmarking (pip install git+https://github.com/qiskit-community/qiskit-device-benchmarking.git)

Requisitos de plano

Algumas etapas deste tutorial não estão disponíveis em todos os planos:

  • Jobs de dry-run (Etapas 2.4 e 3.5) estão disponíveis apenas nos planos Flex, Premium e On-Prem.

  • Sessões (Etapa 4.1) não estão disponíveis no Open Plan. Para executar em batch mode, defina run_calibration = False na Etapa 4.1.

Etapa 1: Especifique um circuito e um observável​

Prepare um circuito espelho de uma evolução temporal trotterizada de um modelo de Ising linear com campo transversal. Espelhe o circuito para cancelar o unitário do circuito e formar um circuito identidade. Como a saída ideal é o estado todo zero, o valor esperado ideal de cada observável ZZZ de um qubit é 1. O espelhamento também dobra a profundidade do circuito, o que amplifica o efeito do ruído.

import numpy as np
from qiskit.circuit import QuantumCircuit
from qiskit.quantum_info import SparsePauliOp

def construct_ising_circuit(
    num_qubits: int,
    num_trotter_steps: int,
    rx_angle: float,
    barrier: bool = True,
) -> QuantumCircuit:
    circuit = QuantumCircuit(num_qubits)

    for _step in range(num_trotter_steps):
        circuit.rx(rx_angle, range(num_qubits))
        if barrier:
            circuit.barrier()
        for first_qubit in (1, 2):
            for idx in range(first_qubit, num_qubits, 2):
                # equivalent to Rzz(-pi/2):
                circuit.sdg([idx - 1, idx])
                circuit.cz(idx - 1, idx)
        if barrier:
            circuit.barrier()

    return circuit

def mirror_circuit(circuit: QuantumCircuit) -> QuantumCircuit:
    mirror_circ = circuit.copy_empty_like()
    mirror_circ.compose(circuit, inplace=True)
    mirror_circ.barrier()
    mirror_circ.compose(circuit.inverse(), inplace=True)
    mirror_circ.measure_active()
    return mirror_circ
num_qubits = 20
observables = [
    SparsePauliOp("I" * ((num_qubits - 1) - q) + "Z" + "I" * q)
    for q in range(num_qubits)
]

# Free parameters of the demonstration circuit: the number of Trotter steps
# sets the circuit depth, and rx_angle is the transverse-field rotation angle
# applied in each step (pi/4 makes the dynamics non-Clifford)
num_trotter_steps = 5
rx_angle = np.pi / 4

circuit = construct_ising_circuit(
    num_qubits, num_trotter_steps, rx_angle, barrier=False
)
mirrored_circuit = mirror_circuit(circuit)
mirrored_circuit.draw(
    "mpl", fold=-1, scale=0.3, idle_wires=False, measure_arrows=False
)

Etapa 2: Otimize para a execução em hardware quântico​

2.1 Use calibração alternativa, se aplicável​

A IBM® calibra suas QPUs periodicamente para um bom desempenho em casos de uso gerais. Algumas cargas de trabalho, porém, se beneficiam de instruções cujos parâmetros são ajustados de forma diferente. Para mais informações, consulte Instruções com calibração especial.

Este tutorial usa um conjunto alternativo de dados de calibração chamado slow_gates_ac. Essa calibração contém uma porta cz mais lenta e modula o viés do sistema de dois níveis (TLS) para estabilizar os erros do dispositivo ao longo do tempo. Essas mudanças beneficiam métodos de mitigação de erros que dependem de um modelo de ruído aprendido. A calibração slow_gates_ac está disponível apenas em QPUs Heron. Se você executar em uma QPU Nighthawk, use slow_gates.

from qiskit_ibm_runtime import QiskitRuntimeService

service = QiskitRuntimeService()
# Use slow_gates_ac because this tutorial uses a noise-learning-based mitigation method
backend = service.backend("ibm_kingston", calibration_id="slow_gates_ac")

2.2 Execute o benchmarking do dispositivo em tempo real​

Uma das etapas mais críticas da transpilação é a seleção do layout, que mapeia os qubits virtuais de um circuito para os qubits físicos do dispositivo de destino. Um bom layout minimiza o número de operações SWAP necessárias e coloca o circuito nos qubits de melhor desempenho, então a qualidade do layout inicial pode afetar significativamente a qualidade dos seus resultados.

Rotinas periódicas de benchmarking são executadas em toda QPU da IBM para relatar o desempenho atual de seus qubits: tempos de relaxação (T1T_1T1​), tempos de coerência (T2T_2T2​), erros de leitura e erros de portas de um e dois qubits. O transpilador do Qiskit usa essas métricas durante a seleção do layout.

As propriedades dos qubits supercondutores, porém, podem variar em escalas de tempo mais curtas, e defeitos transitórios, conhecidos como TLSs, podem degradar temporariamente um qubit que tinha bom desempenho no momento da calibração. Se o transpilador usa informações desatualizadas, ele não consegue selecionar o melhor layout. Por isso, pode valer a pena gastar um pouco de tempo de QPU para caracterizar o dispositivo antes de selecionar um layout.

Consulte o tutorial Atualizar as propriedades do backend com benchmarking em tempo real para um passo a passo detalhado. A suíte de caracterização monta vários experimentos, envia vários jobs e ajusta os resultados. Esse processo pode levar alguns minutos no total. Ative o logging em nível INFO para que cada etapa imprima seu progresso enquanto executa.

import sys
import logging

logger = logging.getLogger("qiskit_device_benchmarking")
logger.setLevel(logging.INFO)
logger.addHandler(logging.StreamHandler(stream=sys.stdout))

2.4 Visualize o tempo do circuito​

Além das instruções de um circuito, você pode querer visualizar o agendamento do circuito para encontrar tempo ocioso nos qubits ou alinhamento ineficiente de instruções. Você obtém as informações de temporização mais detalhadas e precisas do IBM Quantum Compute Service usando o modo dry-run.

O circuito deste tutorial é estático, então seu agendamento não é muito informativo. Você pode obter informações de temporização semelhantes localmente a partir do circuito e das propriedades do backend, por exemplo usando o timeline drawer incluído no Qiskit. Este tutorial inclui esta etapa para mostrar como solicitar e visualizar as informações de temporização. As informações de temporização do serviço são mais úteis para circuitos dinâmicos. Circuitos dinâmicos contêm medições no meio do circuito, operações condicionais e feedforward, que adicionam operações implícitas, como a difusão dos resultados de medição e a determinação de ramificações. A temporização dessas operações não pode ser determinada apenas a partir do circuito e das propriedades do backend.

Consulte Visualizar o tempo do circuito para mais informações. O tempo agendado do circuito está disponível apenas para jobs de Sampler e Executor, então a célula a seguir envia o circuito em modo dry-run usando Sampler. Jobs que você envia em modo dry-run não são executados em QPUs reais e não são cobrados.

from qiskit_ibm_runtime.executor_sampler import Sampler

sampler = Sampler(backend)
# Request timing information in the result metadata
sampler.options.experimental = {
    "execution": {
        "scheduler_timing": True,
    },
}

# Specify dry_run=True to submit in dry-run mode
sampler_job = sampler.run([isa_circuit], dry_run=True)
job_result = sampler_job.result()
circuit_schedule = job_result[0].metadata["compilation"]["scheduler_timing"]
circuit_schedule_timing = circuit_schedule["timing"]

    included_channels=None,
    filter_readout_channels=False,
    filter_barriers=False,

Etapa 3: Aplique mitigação de erros e teste localmente​

3.1 Cliffordize o circuito​

O custo de uma simulação ruidosa geral cresce exponencialmente com o número de qubits, e a maioria dos laptops não consegue simular mais do que cerca de 32 qubits. Por isso, primeiro converta o circuito em um circuito de Clifford, que um simulador de estabilizadores consegue tratar de forma muito mais eficiente. A conversão arredonda cada ângulo de rotação para um ângulo de Clifford, então o circuito simulado aproxima o circuito original em vez de reproduzi-lo.

from qiskit.transpiler import PassManager
from qiskit_ibm_runtime.transpiler.passes import ConvertISAToClifford

clifford_circuit = PassManager([ConvertISAToClifford()]).run(isa_circuit)
clifford_pubs = [(clifford_circuit, isa_observables)]

3.2 Aplique PEC com TREX​

Pode ser difícil selecionar métodos de mitigação de erros que equilibrem custo e precisão para o seu experimento específico. Você pode usar a skill de agente de IA select-error-mitigation para analisar os métodos disponíveis para a sua carga de trabalho. A skill apresenta um relatório resumido que explica se cada método foi selecionado e por quê.

Consulte o repositório do GitHub Qiskit AI skills para mais informações. Este tutorial usa PEC com TREX diretamente, para que você possa concluí-lo sem um agente de IA.

PEC é uma técnica que mitiga o ruído quântico quando você calcula valores esperados de observáveis. Em condições ideais, a PEC pode produzir uma estimativa não enviesada dos valores esperados. Ela aprende o ruído de cada camada de portas de dois qubits e depois executa um conjunto de circuitos que, em média, aplicam o inverso desse ruído. A PEC usa Pauli twirling para moldar o ruído em um canal de Pauli, que pode ser aprendido e invertido de forma eficiente.

Na prática, a PEC é tão precisa quanto o modelo de ruído aprendido. O modelo esparso de Pauli-Lindblad inclui apenas termos de erro de um e dois qubits em qubits vizinhos, e não consegue capturar totalmente efeitos como crosstalk entre qubits distantes ou erros correlacionados no tempo. O ruído do dispositivo também pode variar entre o aprendizado de ruído e a execução. A PEC não cancela o ruído que o modelo deixa de captar e compensa em excesso o ruído que o modelo superestima. Por isso, os resultados mitigados ainda podem se desviar dos valores ideais em qualquer direção.

TREX é uma técnica que mitiga erros de medição e é útil quando você estima os valores esperados de observáveis de Pauli. Ela se baseia em measurement twirling, que diagonaliza a matriz de transferência do erro de leitura e facilita sua inversão. A TREX aprende um termo de reescala a partir do canal de ruído diagonal, medindo circuitos de calibração com twirling inicializados no estado zero. Você pode habilitar PEC e TREX ao mesmo tempo definindo as opções de Estimator. Este tutorial usa as implementações do lado do cliente das interfaces SamplerV2 e EstimatorV2 do Qiskit, introduzidas no qiskit-ibm-runtime v0.50.0. Essas primitivas do lado do cliente realizam localmente a maior parte do pré e do pós-processamento e delegam a execução à primitiva Executor. Quando as primitivas são executadas no lado do cliente, você tem mais transparência, feedback mais rápido na depuração e controle mais fino.

As primitivas do lado do cliente implementam a mesma API das primitivas legadas do lado do servidor. Por isso, normalmente você pode migrar para as primitivas do lado do cliente alterando apenas a instrução de importação. Habilite o log em nível INFO para ver o progresso do pré e do pós-processamento do lado do cliente.

import logging

logger = logging.getLogger("qiskit_ibm_runtime")
logger.setLevel(logging.INFO)
from qiskit_ibm_runtime.executor_estimator import Estimator

estimator = Estimator(mode=backend)
# Enable TREX
estimator.options.resilience.measure_mitigation = True
# Enable PEC
estimator.options.resilience.pec_mitigation = True

3.3 Aprenda modelos de ruído e execute o circuito cliffordizado​

Tanto a PEC quanto a TREX exigem aprendizado de ruído, que você pode fazer com NoiseLearnerV3. As etapas são as seguintes:

  1. Encontre as camadas únicas de portas de dois qubits e as camadas de medição no circuito, para os protocolos Pauli-Lindblad e TREX, respectivamente.

  2. Passe as camadas para NoiseLearnerV3 para aprender os modelos de ruído.

  3. Converta os modelos de ruído aprendidos em mapas de Pauli-Lindblad.

O Estimator não usa um modelo de ruído TREX previamente aprendido. Em vez disso, ele realiza seu próprio aprendizado de TREX. O código a seguir aprende ambos os modelos mesmo assim, porque a simulação ruidosa usa o modelo de leitura aprendido.

Consulte Noise learning helper para mais informações sobre NoiseLearnerV3. Além do experimento de aprendizado de ruído, execute o circuito cliffordizado na QPU. Essa etapa nem sempre é necessária, mas fornece uma comparação para os resultados simulados na Etapa 3.4.4. Execute ambos em um batch para minimizar a variação do perfil de ruído entre os dois.

pubs = [(isa_circuit, isa_observables)]

3.4 Realize a simulação local​

3.5 Estime o uso​

O principal objetivo do modo dry-run é estimar o uso. Diferentemente do modo local, o modo dry-run envia o job ao IBM Quantum Compute Service, que retorna uma estimativa de uso precisa, mas dados de resultado aleatórios. Etapa 4: Execute no hardware​

4.1 Inicialize uma sessão e execute a calibração​

A calibração da QPU otimiza muitos parâmetros que definem os sinais elétricos que acionam as portas e operações quânticas. Os jobs de calibração são executados ao longo do dia entre os jobs dos usuários, mas não durante uma sessão ativa. Esses parâmetros podem variar em um curto período de tempo. Para obter os melhores resultados possíveis, considere acionar a calibração no início de uma sessão ou periodicamente durante uma sessão longa.

Atualmente, apenas a calibração de leitura é suportada, e ela leva aproximadamente cinco minutos de tempo real (wall-clock).

Plote os resultados de hardware mitigados e não mitigados junto com os valores ideais. Como o circuito é um circuito espelho, todo valor ideal é 1, então a distância entre cada ponto e a linha tracejada mostra o erro restante. Para melhorar ainda mais os resultados, você pode tentar o seguinte:

  • Aumente o número de shots ou de randomizações para reduzir a incerteza estatística das estimativas mitigadas. O custo cresce com o overhead de amostragem da PEC.

  • Reaprenda o modelo de ruído imediatamente antes do experimento, na mesma sessão, para reduzir o efeito da variação do ruído.

  • Aprenda o modelo de ruído com mais precisão aumentando as opções num_randomizations, shots_per_randomization ou layer_pair_depths de NoiseLearnerV3. Erros nas taxas aprendidas enviesam os resultados mitigados, e shots adicionais de PEC não removem esse viés.

  • Adicione verificações de erros não markovianos para detectar shots que provavelmente foram corrompidos por erros não markovianos, que o modelo de ruído aprendido não descreve. Em seguida, descarte esses shots por pós-seleção. Aplique as mesmas verificações ao aprender o modelo de ruído, usando as opções bit_flip_checks de NoiseLearnerV3. Caso contrário, o modelo aprendido inclui erros que a pós-seleção remove do experimento, e a PEC compensa em excesso por eles. Uma pós-seleção mais rigorosa descarta mais shots, então equilibre o ganho de precisão com o número de shots que você mantém.

4.4 Inspecione os spans de execução​

Quando você envia circuitos com várias configurações, como no gate twirling, o IBM Quantum Compute Service não executa necessariamente todas as configurações do circuito ao mesmo tempo. Em vez disso, ele as agrupa em chunks e executa um chunk por shot loop. Um shot loop é uma única rodada de execução no hardware quântico, na qual cada circuito do chunk é executado pelo número de shots solicitado.

Todos os jobs enviados a uma QPU real exigem algum pré-processamento clássico, como a tradução em pulsos que podem ser enviados ao hardware. Como esse pré-processamento pode ser feito em paralelo, o serviço tira da fila e inicia vários jobs por vez. A QPU, porém, só consegue processar uma unidade de trabalho por vez. Por isso, se o seu job gerar vários chunks, eles podem ser intercalados com os chunks de jobs de outros usuários, e cada chunk pode ter que esperar a sua vez na QPU.

Os metadados do resultado do job informam a temporização de execução na QPU para cada chunk. A visualização a seguir mostra se há lacunas significativas entre as execuções dos chunks do seu job. Se as lacunas forem maiores do que o seu experimento consegue tolerar, você pode querer executar o job novamente ou usar o modo de execução session, que dá à sua carga de trabalho acesso exclusivo à QPU.

Consulte Ver spans de execução para mais informações.

  • Experimente um método de mitigação de erros mais barato, como a extrapolação de ruído zero (ZNE), e use a simulação local e as estimativas de uso do dry-run para comparar seu custo e precisão com os da PEC. A skill de agente de IA select-error-mitigation pode ajudar você a fazer essa escolha.
  • Explore o conjunto completo de caracterização, incluindo o randomized benchmarking, no tutorial Refresh backend properties with real-time benchmarking.
  • Saiba mais sobre as primitivas do lado do cliente e o Executor em Migrar de Sampler e Estimator do lado do servidor para o lado do cliente.
  • Aplique essas ferramentas aos seus próprios experimentos. Comece pelas ferramentas que tratam a sua maior fonte de incerteza, como qualidade do dispositivo, ruído, custo ou temporização de execução.
