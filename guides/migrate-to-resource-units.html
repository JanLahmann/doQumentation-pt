Migre para unidades de recurso (RUs) na IBM Quantum Compute API

A IBM Quantum® Platform agora mede o uso em unidades de recurso (RUs). Uma RU é a unidade que a IBM Quantum usa para medir e cobrar o uso de todas as cargas de trabalho. Antes dessa mudança, a plataforma media o uso como tempo de QPU em segundos ou milissegundos. Para mais informações sobre RUs, consulte Unidades de recurso.

Hoje, a API retorna dois conjuntos de campos: os campos de tempo antigos e os novos campos de RU. Sua integração continua funcionando. Em uma versão futura, a IBM Quantum removerá os campos de tempo. Altere sua integração para ler os campos de RU agora.

Este guia usa os seguintes termos:

  • Carga de trabalho: Um job, uma sessão, um batch ou uma execução de função.

  • Carga de trabalho de QPU: Um job, uma sessão ou um batch. Uma carga de trabalho de QPU é executada somente em uma QPU.

  • Carga de trabalho de função: Uma execução de função. Uma carga de trabalho de função pode usar computação clássica e uma licença de execução, e também pode usar uma QPU.

  • Sessão: Um grupo de jobs que são executados juntos em uma única QPU.

  • Instância: Uma instância de serviço. Ela é dona das cargas de trabalho e tem limites de uso.

  • Plano: O plano de serviço de uma conta. Ele define os limites de uso de todas as instâncias da conta.

nota

Este guia usa a versão 0.57.2 da especificação OpenAPI.

O valor do cabeçalho IBM-API-Version deve ser 2026-04-15 ou uma versão posterior da API com suporte.

As seções a seguir dão os detalhes de cada endpoint.

Jobs​

Endpoints: GET /v1/jobs e GET /v1/jobs/{id}/metrics.

IgnoreLeia no lugar
usage.qpu_charge_time_secondsusage.value

O objeto usage também tem estes campos:

  • usage.unit: A unidade de usage.value. O valor é sempre "resource_units".

  • usage.status: O status de cobrança. O valor é "pending" ou "complete". Se o status for "pending", a plataforma ainda pode alterar o valor. Não use um valor pendente como o uso final.

  • usage.details[]: O uso de cada métrica de cobrança. O value de cada entrada está em RUs.

Example:

"usage": {
  "qpu_charge_time_seconds": 15,  // old field: disregard
  "value": 0.250005,              // new field: read this
  "unit": "resource_units",
  "status": "complete",
  "details": [
    { "value": 0.250005, "unit": "resource_units", "metric": { "id": "…", "value": 15 } }
  ]
}

O campo usage.details[].metric.value não é o uso em RUs. É a quantidade da métrica que a plataforma usou para calcular as RUs. Cada métrica tem sua própria unidade. Por exemplo, a unidade de uma métrica de QPU é segundos. Para ler o uso, use usage.details[].value.

Cargas de trabalho​

Endpoint: GET /v1/workloads.

Cada item em workloads[] tem um objeto usage. Esse objeto tem os mesmos campos do objeto usage de um job.

IgnoreLeia no lugar
workloads[].usage.qpu_charge_time_secondsworkloads[].usage.value

Se uma carga de trabalho ainda estiver em execução, usage é null.

Cargas de trabalho de função​

O uso de uma carga de trabalho de função é medido em RUs, assim como o de uma carga de trabalho de QPU. Uma carga de trabalho de função pode usar mais de uma métrica:

  • Uso de QPU. É medido por segundo de tempo quântico. Consulte Modos de execução.

  • Uso de computação clássica. É medido por segundo de tempo clássico.

  • Custo da licença de execução. É medido por carga de trabalho, com base no tamanho do problema passado a uma função.

A plataforma converte a quantidade de cada métrica em RUs. Assim, todos os valores de uso estão em RUs:

  • usage.value é o uso da carga de trabalho, em RUs.

  • usage.details[].value é o uso de uma métrica, em RUs.

  • usage.details[].metric.value é a quantidade da métrica, na unidade dessa métrica. Não está em RUs.

Se você exibir ou somar valores de uso, use usage.value e usage.details[].value. Não use usage.details[].metric.value.

Sessões​

Endpoints: POST /v1/sessions e GET /v1/sessions/{id}.

IgnoreLeia no lugar
elapsed_time (segundos)usage.value

O objeto usage da sessão tem unit e details[]. Esses campos funcionam da mesma forma que no objeto usage do job, com exceção do campo status, que é omitido para sessões.

Os campos interactive_ttl, max_ttl e active_ttl não mudam. Eles são limites de tempo (TTL significa "time to live"), não uso. A unidade deles continua sendo segundos.

Uso da instância​

Endpoint: GET /v1/instances/usage.

IgnoreLeia no lugar
usage_consumed_secondsusage_consumed_ru
usage_limit_secondsusage_limit_ru
usage_allocation_secondsusage_allocation_ru

Os campos usage_limit_reached, usage_period e time_available_at não mudam.

Planos da conta​

Endpoint: GET /v1/accounts/{id}.

Cada item em plans[] tem estas mudanças:

IgnoreLeia no lugar
plans[].usage_limit_secondsplans[].usage_limit_ru
plans[].usage_allocation_secondsplans[].usage_allocation_ru
plans[].unallocated_usage_secondsplans[].unallocated_usage_ru

Instâncias de serviço na Resource Controller API​

A IBM Cloud® Resource Controller API é uma API separada. Você a usa para criar e atualizar instâncias de serviço. Se você cria ou atualiza instâncias com essa API, altere também os parâmetros da instância.

Ao criar ou atualizar uma instância, envie estes parâmetros na requisição:

Não envieEnvie no lugarTipo do novo parâmetro
instance_limit_secondsinstance_limit_ruNúmero ou null
usage_allocation_secondsusage_allocation_ruNúmero ou null

Os parâmetros têm estes significados:

  • Limite da instânciaO uso máximo da instância. Se você não enviar um limite no Open Plan, o padrão é o equivalente em RUs a 10 minutos.

  • Alocação de uso: A parcela de uso da instância. O escalonador de compartilhamento justo usa esse valor para definir a prioridade da instância na fila. A alocação não se aplica a instâncias Pay-As-You-Go.

Ao ler uma instância, o objeto extensions na resposta contém os campos antigos e os novos. Ignore instance_limit_seconds e usage_allocation_seconds. Leia instance_limit_ru e usage_allocation_ru.

Para mais informações, consulte a documentação da REST API do IBM Quantum Compute Service.

Análise de uso​

Endpoints: GET /v1/analytics/usage, GET /v1/analytics/usage_grouped e GET /v1/analytics/usage_grouped_by_date.

Os três endpoints têm os mesmos campos de uso. Os dois endpoints agrupados retornam esses campos para cada grupo ou cada data.

Os campos antigos de uso de analytics estão em milissegundos, não em segundos.

Estes campos de função são novos. Eles não têm um campo antigo em milissegundos:

  • functions_usage_ru

  • avg_functions_usage_ru

  • max_functions_usage_ru

  • functions_classical_usage_ru

  • functions_license_cost_ru

O total em usage_ru inclui mais do que o total em usage:

  • usage é a soma do tempo de QPU de sessões, jobs individuais e funções.

  • usage_ru é a soma do uso de sessões, jobs individuais e funções. Para funções, também inclui computação clássica e custo de licença.

Assim, usage_ru não é apenas usage em outra unidade.

Os campos queue_time, avg_queue_time e max_queue_time não mudam. Eles medem tempo de espera, não uso. A unidade deles continua sendo milissegundos.

Campos que não mudam​

Estes campos contêm valores de tempo, mas não medem uso. A IBM Quantum não planeja substituí-los:

  • wait_time_seconds em backends: A espera estimada na fila.

  • circuits_execution_time_ns em GET /v1/jobs/{id}/metrics: O tempo que o job foi executado na QPU.

  • interactive_ttl, max_ttl e active_ttl em sessões.

  • queue_time, avg_queue_time e max_queue_time em analytics.

  • rep_times e circuit_duration na configuração do backend.

Etapas de migração​

  1. Encontre cada campo antigo no seu código. Procure por qpu_charge_time_seconds, elapsed_time, os campos _seconds deste guia e os campos de analytics em milissegundos.

  2. Troque cada campo antigo pelo campo de RU indicado nas tabelas deste guia.

  3. Se você cria ou atualiza instâncias de serviço com a Resource Controller API, envie instance_limit_ru e usage_allocation_ru. Não envie os parâmetros _seconds.

  4. Altere os rótulos na sua interface de usuário. Mostre "RU" ou "unidades de recurso", não "segundos" ou "minutos". Não converta RUs em tempo. Não existe uma taxa fixa entre RUs e tempo.

  5. Se você lê usage.details[], use value para o uso em RUs. Não use metric.value, porque a unidade dele é a unidade da métrica.

  6. Se usage.status for "pending", mostre o valor como provisório.

  7. Se um campo de RU estiver ausente ou for null, use a mesma lógica que você usa hoje para o campo antigo.
